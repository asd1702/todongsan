# 인기 마켓 예측 참여 입장 제한

인기 마켓 하나에 예측이 처리 용량보다 많이 몰려도 Market의 다른 기능(조회, 다른 마켓 예측)이 멈추지 않게 한다.
관련: `SPEND_CIRCUIT_BREAKER.md` §1 run 1, `EXPERIMENT_RESULTS.md` ⑰ ⑲.

## 1. 문제

- 같은 마켓의 예측은 가격(선택지 풀) 갱신 때문에 확정 트랜잭션(TX2)이 마켓·선택지 행 잠금으로 한 줄로 처리된다. 실제 MP와 함께 잰 처리 용량은 약 27건/s(1건 약 37ms).
- TX2는 **DB 커넥션을 쥔 채 잠금을 기다린다.** 용량보다 많이 들어오면 커넥션 10개(Hikari 기본)를 인기 마켓 예측이 모두 잡는다.
- run 1(50/s, 장애 없음): 포인트와 무관한 마켓 조회까지 30초 타임아웃, 톰캣 사용 스레드 183, 지표 응답 없음. 클라이언트가 포기한 요청도 서버는 끝까지 처리했다(확정 4753 중 클라이언트가 받은 것 1745).

순서대로 처리해야 하는 구간이 하나라서, 동시에 들어온 요청이 몇 건만 있어도 처리기는 쉬지 않는다. 그 이상은 처리량을 늘리지 못하고 대기만 늘린다(리틀의 법칙). 50건이 동시에 기다리면 대기 약 1.9초, 처리량은 그대로 약 27/s.

업계 사례: 거래소는 종목(마켓)별로 순서대로 처리하고(LMAX 단일 처리기), 감당 못 하는 주문은 즉시 거절한다(BitMEX load shedding, 503 "system overloaded").

## 2. 설계

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| A1 | 단위 | **마켓별 동시 처리 한도** (in-flight 예측 수) | 병목이 마켓 단위다. 다른 마켓은 서로 막지 않는다 |
| A2 | 넘치면 | **즉시 거절** (기다리지 않음) | 앱에서 기다리면 톰캣 스레드를 잡는다 (run 1) |
| A3 | 판정 위치 | **예측 생성(TX1) 전**, 서킷 허가보다 먼저 | 거절된 요청은 DB·MP를 쓰지 않는다. 로컬 판정이라 가장 싸다 |
| A4 | 범위 | 허가부터 응답까지(TX1 → MP 차감 → TX2) | 커넥션을 쥐는 TX2와 그 앞 단계를 함께 센다. 끝나면 반환 |
| A5 | 응답 | 503 **`SERVICE_UNAVAILABLE`** (공통 코드, ERROR_POLICY §2-10 "일시적인 서버 과부하", Market `CommonErrorCode`에 추가) | 같은 의미의 공통 코드가 있으면 새로 만들지 않는다 (§8). 서킷 거절(`EXTERNAL_SERVICE_UNAVAILABLE`)과 errorCode로 구분된다 |
| A6 | 한도 | `market.prediction.admission.max-in-flight-per-market`. 0이면 제한 없음. **기본값은 §3 측정으로 정한다** (추정 4~6: 처리량을 다 쓰면서 커넥션 풀의 절반 이하) | 리틀의 법칙 추정은 측정으로 확인한다 |
| A7 | 인스턴스 | 인스턴스마다 따로 | 커넥션 풀도 인스턴스마다다. 전역 정확한 한도(공유 카운터)는 지금 필요 없다 |
| A8 | 정합성 | 영향 없음. 거절은 아무것도 만들지 않고, 허가 뒤 경로는 지금과 같다 | 같은 멱등성 키로 다시 시도할 수 있다 |

구현: 마켓 ID별 `Semaphore`(`tryAcquire`, 기다리지 않음). 마켓 수만큼 작은 객체가 남지만 마켓 수가 작아 지우지 않는다.

## 3. 검증 계획

1. 단위: 한도만큼은 통과하고 넘치면 503 + row·MP 호출 없음, 다른 마켓은 영향 없음, 끝나면(성공·실패·예외) 반환, 0이면 제한 없음. 변형 검사.
2. E2E (run 1 조건, 인기 마켓 50/s + **다른 마켓 예측 5/s** + 마켓 조회 10/s, 장애 없음): 한도 2 / 4 / 8 / 16 / 없음.
   인기 마켓 확정 건/s, 거절률, 다른 마켓 예측·조회 p95, DB 커넥션 사용·대기. **처리량을 거의 잃지 않으면서 다른 기능이 정상인 가장 작은 한도**를 기본값으로 한다.

- **한도가 있으면 조회와 다른 마켓이 산다** (30초 → 수십~수백 ms). 제한 없음에서는 인기 마켓 확정 27/s가 나오지만 인기 예측 p95가 30초라 사용자는 대부분 타임아웃을 보고, 서버는 포기한 요청까지 처리한다.
- **§2의 추정(한도 4~6이면 처리량을 다 쓴다)은 틀렸다.** 한도 4에서 15.4/s(최대의 약 59%). 자리 하나가 줄 서는 확정 단계만이 아니라 예측 생성 → MP 차감 → 확정 전체를 차지해서, 자리를 쥔 요청이 MP를 기다리는 동안 줄 서는 구간이 논다.
  (자리를 확정 단계에만 걸면 이미 차감한 요청을 거절해야 해서 안 된다. 차감 전에 판정해야 한다 — A3)
- 한도 2는 **평범한 마켓(5/s)도 2~4% 거절**한다. 한도 16부터는 커넥션 대기가 생기고(10~14) 조회가 240ms로 느려진다 → 보호가 약해지기 시작한다.
- **추천 기본값 8**: 보호 유지(조회 13~16ms, 다른 마켓 거절 0, 커넥션 대기 0~3) + 인기 마켓 18~19/s(제한 없음의 약 70%, 그런데 응답을 받는 처리량은 오히려 높다).
