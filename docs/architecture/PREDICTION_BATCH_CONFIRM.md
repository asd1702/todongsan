# 예측 확정 묶음 처리 (인기 마켓 2단계)

같은 마켓의 예측 확정(TX2)을 모아 트랜잭션 1개로 처리해, 마켓당 처리 상한을 올린다.
관련: `HOT_MARKET_ADMISSION.md` §7(시간 분해), `EXPERIMENT_RESULTS.md` ㉔.

## 1. 근거

- 마켓당 상한(약 27/s)은 확정 트랜잭션이 **마켓 행 잠금을 commit 끝까지 쥐는 시간**(평균 34ms)에서 온다. 그중 실제 SQL은 7~9%, commit(fsync 2회)이 55~63%, 문장 사이 왕복이 약 30%.
- 같은 행 잠금으로 줄을 서서 MySQL group commit도 쓰지 못한다.
- N건을 잠금 1번·commit 1번으로 묶으면 1건당 잠금 시간 ≈ (commit + 왕복) / N + 실제 일. 추정 N=10 약 175/s, N=50 약 320/s (임계 구역만의 상한).
- 업계 사례: 알리바바 AliSQL/RDS **Inventory Hint** — 같은 행을 갱신하는 동시 요청을 리더 스레드가 모아 한 번에 적용·commit하고, 나머지는 결과만 받는다. 단일 행 초당 약 31,000건.

## 2. 범위

- **요청 경로의 확정(TX2)만** 묶는다. 예측 생성(TX1)과 MP 차감은 회원별이라 이미 병렬이다.
- 대사(`confirmPredictionForReconciliation`)는 1분 주기라 건별 그대로 둔다.
- 가격 규칙은 바꾸지 않는다. 묶음 안에서도 **한 건씩 순서대로** 가격을 계산하므로 결과는 같은 순서로 건별 처리한 것과 숫자 하나까지 같다.

## 3. 결정

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| P1 | 모으는 방식 | **리더-팔로워** (알리바바 방식). 요청 스레드가 마켓 큐에 확정 요청을 넣고, 처리 중인 리더가 없으면 자신이 리더가 되어 큐를 비울 때까지 묶음을 처리한다. 나머지는 결과(Future)를 기다린다 | 별도 스레드·대기 시간(window)이 필요 없다. 한가할 때는 묶음 크기 1이라 지연이 늘지 않고, 붐빌수록 앞 묶음이 commit하는 동안 쌓인 만큼 자연스럽게 커진다 |
| P2 | 순서 | 마켓 큐에 들어온 순서(FIFO) = **MP 차감이 끝난 순서** | 확정은 차감이 끝나야 할 수 있다. 처음 도착 순서를 지키려면 차감이 늦은 앞 요청을 뒤 요청이 기다려야 한다(head-of-line blocking). 지금은 잠금 경쟁(MySQL CATS) 순서라 이보다 명확하다 |
| P3 | 묶음 크기 상한 | `max-batch-size` 기본 50 (측정으로 확정: 10 / 25 / 50 / 100) | 리더 혼자 오래 잡지 않게, 묶음 TX가 너무 커지지 않게 |
| P4 | 묶음 트랜잭션 | 마켓 잠금 → 선택지 잠금 → 예측들 `IN (...) FOR UPDATE` → **받은 순서대로 메모리에서 건별 검증·가격 계산** → 쓰기: 마켓 풀 1문장, 선택지 최종 상태(선택지 수만큼 또는 VALUES JOIN 1문장), 가격 이력 다중 행 INSERT, 예측 확정 VALUES JOIN 1문장 → commit 1번 | 정산 결과 반영(ASYNC_POINT_FLOW §17.6)과 같은 패턴. 왕복도 같이 준다 |
| P5 | 건별 결과 | 건마다 지금과 같은 결과: 성공 응답, 또는 지금 경로가 던지는 예외(가격 갱신 충돌 등). 확정 못 한 건은 쓰지 않는다(POINT_PENDING 유지 → 대사) | 요청 경로 동작을 바꾸지 않는다 |
| P6 | 묶음 실패 | 묶음 TX가 예외(교착, DB 오류)면 롤백 후 그 묶음을 **건별 기존 경로**(`confirmPrediction`)로 하나씩 처리 | 결과 반영 consumer와 같은 원칙: 묶음이 실패해도 원인 건만 실패 |
| P7 | 기다리는 쪽 | Future 대기(상한 `wait-timeout`). DB 커넥션을 쥐지 않는다. 리더만 커넥션 1개 | 잠금 대기 중 커넥션을 쥐던 지금보다 커넥션 사용이 준다 |
| P8 | 리더 이탈 | 리더가 예외로 끝나도 맡은 Future는 모두 완료(예외 포함)하고, 리더 자리를 놓은 뒤 큐를 다시 확인한다 | 큐에 남은 건이 주인 없이 남지 않게 (흔한 경합 버그) |
| P9 | 인스턴스 | 인스턴스마다 따로 묶는다. 인스턴스 사이 순서는 DB 잠금이 정한다 | 정확성은 잠금으로 유지되고, 잠금 횟수는 "건 수"에서 "묶음 수"로 준다 |
| P10 | 스위치 | `market.prediction.batch-confirm.enabled` (before/after, 롤백) | 지금까지와 같은 방식 |

## 4. 검증 계획

1. **동등성 (mysqlit)**: 같은 마켓·같은 예측 순서를 건별 경로와 묶음 경로로 각각 확정 → 선택지 풀·가격·계약 수량·가격 이력·예측 상태가 숫자 하나까지 같다. 묶음 안에 확정 불가 건(이미 확정, 다른 상태) 섞기.
2. 리더-팔로워: 동시 요청이 묶이는지(묶음 크기 > 1), 리더 예외 시 모든 Future 완료, 리더 교대 시 큐에 남은 건 없음, 묶음 실패 → 건별 처리.
3. 변형 검사: 순서 뒤집기, 묶음 안 가격 누적 빠뜨리기, 리더 자리 미반환, 실패 건을 쓰기 등.
4. 성능: 인기 마켓 50/s(한도 8) before/after, 묶음 크기 10/25/50/100, 다른 마켓·조회 보호 유지, `confirm-breakdown.sh`로 1건당 잠금 시간.
5. 입장 제한 재조정: 묶음이 커넥션을 덜 쓰므로 마켓별·전체 한도를 다시 잰다.

## 5. 구현·측정 결과 (결과 ㉕)

**구현**
- `MarketPredictionTransactionService.applyConfirmation`: 건별·묶음이 같이 쓰는 가격 계산. 기존 코드는 선택지를 바꾼 뒤 검증해, 묶음에서는 거절된 건의 흔적이 뒤 건 가격에 남을 수 있었다 → 모든 검증 뒤에만 바꾼다.
- `confirmPredictionsInBatch`: 마켓·선택지·예측(`IN ... FOR UPDATE`, ID 순) 잠금 → 받은 순서대로 적용 → 마켓 풀 1문장, 선택지 최종 상태, 가격 이력 다중 행 INSERT, 예측 확정 CASE UPDATE 1문장(H2·MySQL 공통) → commit 1번. 같은 예측이 두 번 오면 두 번째는 이미 확정된 것으로 본다.
- `PredictionConfirmBatcher`: 리더-팔로워. 리더 자리를 놓은 뒤 큐를 다시 확인한다(P8). 대기 상한 초과 시 `MARKET_PRICE_UPDATE_CONFLICT`(건별 확정 실패와 같은 응답, 이후 대사가 정리).

**검증**: 동등성(mysqlit: 같은 순서를 건별·묶음으로 확정 → 응답·선택지·마켓 풀·가격 이력·예측 상태 동일 + 절대값), 리더-팔로워(쌓인 요청 한 묶음, 묶음 실패 → 건별, 앞 요청이 끝난 뒤 요청, 리더 교대 직전 요청을 테스트 지점으로 재현), 스트레스(300건 × 20회, 모두 정확히 한 번). 변형 검사 11개 모두 잡힘.
- 같은 계산 코드를 공유하는 두 경로는 동등성만으로 공통 버그를 못 잡는다 → 절대값 단언 추가.
- 리더 자리 미반환·교대 후 재확인 누락은 부하 테스트로는 드러나지 않았다(모든 요청이 리더 작업 중에 들어옴) → 교대 순간을 결정적으로 재현하는 테스트로 잡았다.

- **한도 8에서는 효과가 작다(+10~25%).** 자리 하나가 MP 차감 시간까지 차지해 묶음이 작다(평균 2.6). 병목이 입장 제한으로 옮겨 갔다.

- 부하가 여러 마켓으로 흩어지면 묶을 게 적어 효과가 작다(마켓당 약 6/s).
- run 92(켬 8/16, 50/s)는 PC 전체가 약 35초 멈춰(샘플러 공백 34.8초, MP Hikari "clock leap") 결론에서 뺐다. 이 PC에서 같은 경고가 14번 있었다.

**결정: 묶음 확정 켬, 마켓별 16, 전체 24.** 인기 마켓 약 1.9배(19 → 38건/s), 조회 21ms. 여러 마켓이 붐빌 때 조회 48ms로 16/32(88ms)보다 낫다.
